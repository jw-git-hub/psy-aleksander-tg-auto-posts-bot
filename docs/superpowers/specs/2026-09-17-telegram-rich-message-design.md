# Публикация в Telegram одним сообщением-«Статьёй» — дизайн

Дата: 2026-09-17. Статус: утверждён владельцем в чате, ждёт ревью документа.

## Цель

Сейчас пост уходит в канал двумя сообщениями: `sendPhoto` (картинка), затем
`sendMessage` (текст, лимит 4096). Нужно, чтобы картинка и текст выходили
**одним сообщением**, без поломок текущей публикации.

Первый шаг — только объединение. Тексты, промпт рерайта, фильтры утечек,
лимит длины и Facebook/Instagram не меняются.

## Что такое «Статья»

Пункт «Статья» (англ. «Article») в меню скрепки — редактор расширенных
сообщений Telegram (Rich Text Editor, для пользователей с 14.07.2026, только
Premium). Для ботов — метод `sendRichMessage` (Bot API 10.1, 11.06.2026;
актуальная версия на дату дизайна — 10.3).

Проверенные по https://core.telegram.org/bots/api факты:

- `sendRichMessage(chat_id, rich_message: InputRichMessage, ...)` → обычный
  `Message` (есть `message_id`). Канал поддерживается.
- `InputRichMessage`: ровно одно из `html` / `markdown` / `blocks`, плюс
  `media` (массив `InputRichMessageMedia`: `id` + `InputMediaPhoto`).
  Картинка в HTML — `<img src="tg://photo?id=<id>"/>`, файл —
  `attach://<name>` в multipart-запросе (добавлено в 10.2).
- Лимиты: до 32 768 символов, 500 блоков, 50 медиа.
- Правка — `editMessageText` с полем `rich_message`; удаление — обычное
  `deleteMessage`.
- В старых клиентах вместо поста — заглушка «Unsupported Message — Update
  Telegram».

Противоречие в документации: в одном месте разрешена загрузка файла через
`tg://photo?id=`, в другом сказано «Media blocks support only HTTP and HTTPS
URLs». Требование Premium для ботов в документации не упомянуто. Оба вопроса
закрывает проверка в тестовом канале (см. «Проверка»).

## Рассмотренные варианты

1. **`sendRichMessage` — выбран.** Одно сообщение, картинка загружается
   ботом (как сейчас), запас по длине на будущее. Минус — старые клиенты.
2. `sendMessage` с `link_preview_options` (большое превью) — отклонён:
   картинку выбирает Telegram из og:image источника (не гарантирована),
   под ней карточка сайта-источника, а источники в постах не показываются.
3. `sendPhoto` с `caption` — отклонён: лимит подписи 1024, посты 1000–2000.

## Дизайн

### Переключатель формата

- Ключ `telegram_post_format` в `config.json`: `"classic"` (по умолчанию) или
  `"rich"`. Переопределение через переменную окружения
  `TELEGRAM_POST_FORMAT` — по тому же образцу, что остальные ключи в
  `load_config()`.
- Нет ключа или неизвестное значение → `classic` (неизвестное значение
  логируется предупреждением).
- Ключ добавляется в `config.example.json`.
- Откат — вернуть `classic`, код не трогается.

### `TelegramPublisher` (`publishers/telegram.py`)

- Конструктор получает `post_format: str = "classic"`;
  `_build_publishers()` передаёт значение из конфига.
- `publish()`:
  - `rich` **и** есть `image_bytes` → `_send_rich(text, image_bytes)`;
  - иначе → текущий путь `sendPhoto` + `sendMessage` **без изменений**.
    Пост без картинки в режиме `rich` уходит по-старому.
- Текущий путь выносится в отдельный метод (`_publish_classic`), без
  изменения поведения, чтобы вызывать его и как основной путь, и как
  запасной вариант.

### `_send_rich`

Запрос: multipart `POST .../sendRichMessage`:
- `chat_id`;
- `rich_message` — JSON-строка:
  `{"html": <html>, "media": [{"id": "cover", "media": {"type": "photo", "media": "attach://cover"}}]}`;
- файловая часть `cover` — байты картинки (`image/jpeg`, как в `_send_photo`).

Точную форму полей исполнитель сверяет с официальной документацией
`sendRichMessage` / `InputRichMessage` / `InputRichMessageMedia` перед
реализацией. Если документация расходится с этой схемой — побеждает
документация, расхождение фиксируется в JOURNAL.md.

HTML строится из текста поста:
- первым блоком — `<img src="tg://photo?id=cover"/>`;
- текст экранируется `html.escape` целиком: посты — простой текст, тегов
  рерайт не генерирует, поэтому `<`, `>`, `&` выводятся как есть;
- абзацы — по пустым строкам, каждый в `<p>…</p>`;
- одиночный перенос строки внутри абзаца: `<br/>`, если тег есть в списке
  поддерживаемых в документации; иначе каждая строка — отдельный `<p>`;
- тот же страховочный обрез до 4093 символов, что в `_send_message`
  (обрез до экранирования).

Обработка ответа — та же политика повторов, что у текущих методов:

| Ответ Telegram | Действие |
|---|---|
| `ok: true` | успех: `post_id` = `message_id`, `photo_post_id` = `None`, `post_format` = `"rich"` |
| 429 | ждать `retry_after`, повторить (до `retry_max`) |
| 5xx | ждать 2 с, повторить (до `retry_max`) |
| исключение (тайм-аут, обрыв) | ждать 2 с, повторить (до `retry_max`) |
| попытки исчерпаны | **провал без запасного варианта**: пост мог дойти, повтор другим способом дал бы дубль |
| любой другой отказ (`ok: false`, 400/403/…) | WARNING с описанием ошибки → `_publish_classic` целиком; результат с `post_format` = `"classic"` |

Запасной вариант срабатывает только на явный отказ Telegram: при нём сообщение
гарантированно не создано, и дубля не будет. Если перед отказом была хотя бы
одна попытка с неясным исходом (исключение или 5xx), rich-сообщение могло
всё-таки появиться в канале — тогда отказ считается провалом **без**
запасного варианта. Попытки с 429 неясными не считаются: сообщение при них
не создаётся.

### Результат и трекер тем

- `PublishResult` получает поле `post_format: str | None = None`
  (Facebook/Instagram его не заполняют).
- В запись `posted-topics.json` добавляется `telegram_post_format`: исправлять
  rich-пост нужно через `editMessageText` с `rich_message`, а не с `text`.
- Формирование Telegram-полей записи выносится в маленькую функцию
  (`chat_id`, `message_id`, `photo_message_id`, `post_format`), чтобы её можно
  было протестировать отдельно от `main()`.
- Запись в трекер — по-прежнему только при успехе Telegram.
- Строка лога `Опубликовано: <тема> (цикл N)` не меняется: по ней
  `run_with_retry.sh` определяет успешный запуск.
- В лог пишется, каким форматом ушёл пост, и причина перехода на classic.

### Что не меняется

Рерайт и промпт, `clean_ai_artifacts`, `_validate_rewritten_post`,
`_check_semantic_leak`, `POST_MAX_LEN = 4096`, дедупликация, Facebook и
Instagram, `run_with_retry.sh`, cron.

## Проверка

### Автотесты (pytest, без сети)

Сейчас настоящих тестов нет (`pytest` в venv есть, `test_publishers.py` —
smoke-скрипт). Добавляются `tests/` и `requirements-dev.txt` с `pytest`.
`requests.post` и `time.sleep` подменяются заглушками.

Сначала — **характеризационные тесты текущего поведения**, которые должны
пройти на коде до изменений:
- classic: `sendPhoto` (multipart, `chat_id`, файл `photo`), затем
  `sendMessage` (JSON: `chat_id`, `text`, `parse_mode: "HTML"`,
  `disable_web_page_preview: true`);
- фото не ушло → текст всё равно отправляется;
- 429 → ожидание `retry_after` и повтор; 5xx → повтор;
- «can't parse entities» → повтор без `parse_mode`;
- обрез текста длиннее 4096.

Затем — тесты нового поведения:
- переключатель: нет ключа / мусор → classic; `rich` → rich;
- rich без картинки → classic;
- rich: ровно один запрос `sendRichMessage`, файл `cover`, корректный JSON
  `rich_message`;
- экранирование `<`, `&`, кавычек; абзацы и переносы строк;
- явный отказ → classic, ровно одна публикация, `post_format="classic"`;
- тайм-аут / исчерпанные 5xx → провал, **ни одного** вызова classic;
- тайм-аут, затем явный отказ → провал, **ни одного** вызова classic;
- 429, затем явный отказ → classic;
- 429 → ожидание и повтор;
- функция полей записи трекера: rich и classic.

Запуск из worktree: `../../../venv/bin/python3 -m pytest -q` (venv лежит в
основной папке проекта).

### Тестовый канал

- Ключ `telegram_test_chat_id` в `config.json` (+ `TELEGRAM_TEST_CHAT_ID`).
- Скрипт `preview_telegram_format.py` (в корне, рядом с
  `test_publishers.py`):
  - **не** трогает `posted-topics.json`, **не** вызывает Claude, **не**
    публикует в Facebook/Instagram;
  - отказывается работать, если `telegram_test_chat_id` пуст или совпадает
    с `telegram_chat_id`;
  - `--find-chat-id` — вызывает `getUpdates` и печатает id каналов, откуда
    пришли сообщения (владелец пишет что-нибудь в тестовый канал, потом
    запускает скрипт);
  - по умолчанию отправляет в тестовый канал один и тот же образец поста
    в обоих форматах, затем набор неудобных случаев в `rich`: символы
    `< > &` и кавычки, текст около 4000 символов, список через тире,
    эмодзи, несколько абзацев;
  - картинка — `--image <путь>`, по умолчанию первый по алфавиту `.jpg`
    из `docs/screenshots/`.

Владелец смотрит посты на телефоне и компьютере: видна ли картинка,
сохранены ли абзацы, как пост выглядит в списке чатов и в уведомлении.

**Точка остановки:** если Telegram не принимает загруженную картинку
(противоречие в документации) или требует Premium — работа
останавливается и владельцу предлагается изменённый план. Молча
переходить на картинку по ссылке нельзя.

## Внедрение

1. Разработка в отдельном worktree на ветке
   `worktree-telegram-rich-message`. Живой бот (cron, основная папка
   на `main`) изменений не видит.
2. Все автотесты зелёные; ревью кода.
3. Слияние в `main` вне окон публикации: не с 02:50 до 03:30 UTC и не с
   10:50 до 11:30 UTC. Переключатель остаётся `classic`. Ближайший пост
   должен выйти как раньше — проверить по `logs/post.log`.
4. Прогон `preview_telegram_format.py` в тестовом канале, «ок» от
   владельца.
5. `telegram_post_format: "rich"` в `config.json` основной папки. Проверка
   двух ближайших постов (10:00 и 18:00 по Бангкоку) по логу и в канале.
6. Проблемы (в том числе жалобы подписчиков со старым Telegram) →
   `classic`.

Документация: в `CLAUDE.md` (раздел «Формат поста»), `README.md` (русская и
английская части) и `JOURNAL.md` описать оба формата и переключатель.

## Вне рамок

- Оформление: заголовки, выделения, цитаты. Потребует изменения промпта и
  фильтров утечек — следующий шаг.
- Посты длиннее 4096 символов. При срабатывании запасного варианта их
  пришлось бы обрезать.
- Инструмент исправления опубликованных rich-постов.
- Изменения Facebook/Instagram.

## Известные риски

- Подписчики со старыми версиями Telegram увидят заглушку «обновите
  Telegram». Количество таких подписчиков узнать нельзя; ответ на жалобы —
  откат на `classic`.
- Вид rich-поста в уведомлениях и списке чатов в документации не описан —
  проверяется в тестовом канале.
- Поведение при тайм-ауте повторяет текущее (повтор того же запроса):
  риск дубля при потерянном ответе остаётся на прежнем уровне, новых
  путей к дублю не добавляется.
